# 🧪 แผนการทดสอบระบบ (Test Plan & Test Cases) - Portfolio Hub

เอกสารนี้ระบุรายละเอียดของกรณีการทดสอบ (Test Cases) และแผนการประเมินความถูกต้องสำหรับระบบจัดเก็บผลงาน (Portfolio Hub) ซึ่งประกอบไปด้วยส่วน Next.js Frontend, Go REST API, Supabase Database, Background Worker และ Nginx Reverse Proxy

---

## 📌 ขอบเขตการทดสอบ (Scope of Testing)

ระบบแบ่งการทดสอบออกเป็น 5 ส่วนหลัก:
1. **ระบบการยืนยันตัวตนและความปลอดภัย (Authentication & Security)**
2. **ระบบจัดการฐานข้อมูลและ REST API (Backend API)**
3. **ระบบรันเนอร์บิลด์ตู้คอนเทนเนอร์อัตโนมัติ (Background Worker & Docker Runner)**
4. **การนำส่งทราฟฟิกและการเชื่อมเน็ตเวิร์ก (Nginx Reverse Proxy & Docker Network)**
5. **ส่วนติดต่อผู้ใช้งานแผงควบคุมแอดมิน (Frontend Dashboard UI & Interactive Flow)**

---

## 1. ระบบยืนยันตัวตนและความปลอดภัย (Authentication & Security)

| รหัสกรณีทดสอบ | หัวข้อการทดสอบ | ขั้นตอนการดำเนินงาน (Steps) | ผลลัพธ์ที่คาดหวัง (Expected Results) |
| :--- | :--- | :--- | :--- |
| **TC-SEC-01** | การเข้าสู่ระบบด้วย Supabase Auth | 1. ไปที่หน้า `/login`<br>2. กรอก Email และ Password ของแอดมิน<br>3. กดปุ่ม Login | - ระบบสามารถคุยกับ Supabase เพื่อรับ JWT Access Token<br>- บันทึก Session และเปลี่ยนเส้นทางไปยังหน้า `/admin` สำเร็จ |
| **TC-SEC-02** | การป้องกันหน้าเว็บที่เป็นความลับ (Client Middleware) | 1. ทำการ Logout หรือล้างคุกกี้/LocalStorage<br>2. พยายามพิมพ์เข้า URL `/admin` ตรง ๆ | - ระบบ Middleware ของ Next.js บล็อกการเข้าถึง<br>- เปลี่ยนเส้นทางผู้ใช้กลับไปหน้า `/login` ทันที |
| **TC-SEC-03** | การตรวจสอบโทเค็นผ่าน API (JWT Middleware) | 1. ส่งคำขอ `POST /projects` ไปยัง API หลังบ้านโดยไม่มี Header `Authorization`<br>2. ส่งอีกคำขอโดยแนบ JWT โทเค็นที่หมดอายุแล้ว | - API ส่งการตอบกลับเป็นรหัส `401 Unauthorized`<br>- ฐานข้อมูลไม่มีการเพิ่มข้อมูลใหม่ |
| **TC-SEC-04** | การเข้าถึงโปรเจกต์ที่ถูกซ่อน (Visibility Guard) | 1. ผู้ใช้ทั่วไปพยายามเปิดลิงก์ `/projects/:id` ของโปรเจกต์ที่ตั้งค่า `isVisible = false`<br>2. แอดมินพยายามเปิดลิงก์เดิม | - สำหรับผู้ใช้ทั่วไป: แสดงหน้า "Project Not Found (404)"<br>- สำหรับแอดมิน: เปิดดูข้อมูลได้ตามปกติ และมีป้าย "Hidden" บ่งชี้สถานะ |

## 2. ระบบจัดการข้อมูลโปรเจกต์และโปรไฟล์ (Backend REST API)

| รหัสกรณีทดสอบ | หัวข้อการทดสอบ | ขั้นตอนการดำเนินงาน (Steps) | ผลลัพธ์ที่คาดหวัง (Expected Results) |
| :--- | :--- | :--- | :--- |
| **TC-API-01** | การสร้างโปรเจกต์ใหม่พร้อมระบุ Git URL | 1. ยิงคำขอ `POST /projects` พร้อม Body JSON ที่มีโครงสร้างข้อมูลครบถ้วนรวมถึง `gitUrl` | - บันทึกข้อมูลลงตาราง `projects` สำเร็จ<br>- ส่งรหัสตอบกลับ `201 Created` กลับมาพร้อมไอดีใหม่ |
| **TC-API-02** | การแก้ไขข้อมูลโปรเจกต์และ Git URL | 1. ยิงคำขอ `PUT /projects/:id` เพื่อแก้ไขชื่อเรื่องและ `gitUrl` ของโปรเจกต์ | - ข้อมูลคอลัมน์ `title` และ `git_url` ในตารางอัปเดตตรงตามที่ส่งไป<br>- ส่งรหัสตอบกลับ `200 OK` |
| **TC-API-03** | การอัปโหลดและผูกไฟล์เอกสารประกอบโปรเจกต์ | 1. อัปโหลดไฟล์ PDF ผ่าน `POST /upload`<br>2. ผูกลิงก์ของไฟล์เข้ากับโปรเจกต์ผ่าน `POST /projects/:id/documents` | - ข้อมูลถูกเพิ่มลงตาราง `project_documents`<br>- เอกสารแสดงผลลิสต์ร่วมกับโปรเจกต์ใน API GET |
| **TC-API-04** | ลบโปรเจกต์และเอกสารที่เกี่ยวข้อง | 1. เรียกคำขอ `DELETE /projects/:id` บนโปรเจกต์ที่มีเอกสารผูกไว้ | - ลบเรคอร์ดโปรเจกต์สำเร็จ<br>- ข้อมูลเอกสารใน `project_documents` ถูกลบออก (Cascade/Cleanup) |

## 3. ระบบบิลด์และรันแอปพลิเคชันอัตโนมัติ (Background Worker & Docker Runner)

| รหัสกรณีทดสอบ | หัวข้อการทดสอบ | ขั้นตอนการดำเนินงาน (Steps) | ผลลัพธ์ที่คาดหวัง (Expected Results) |
| :--- | :--- | :--- | :--- |
| **TC-WRK-01** | การจับคิวงานแบบ Polling Loop | 1. สร้าง Deployment ใหม่เพื่อลงทะเบียนคิวในฐานข้อมูลสถานะ `Pending`<br>2. ตรวจสอบหน้าคอนโซลของบริการ `worker` | - สัญญาณ Loop ของ Worker ตรวจพบข้อมูลงานใหม่ภายใน 5 วินาที<br>- ปรับสถานะงานในฐานข้อมูลเป็น `Building` พร้อมเริ่มเขียน Log |
| **TC-WRK-02** | การโคลน Git Repository อัตโนมัติ | 1. ให้ Worker เริ่มขั้นตอนการดาวน์โหลดโค้ดผ่านคำสั่ง Git | - ดึงโค้ดลงมาเก็บในพื้นที่ชั่วคราว `/tmp/builds/project-<slug>` สำเร็จ<br>- ระบบเขียนรายงานผลการโคลนลงใน Logs ในระบบฐานข้อมูล |
| **TC-WRK-03** | การเลือกใช้/สร้าง fallback Dockerfile | 1. ทดลอง Deploy โปรเจกต์ที่ไม่มีไฟล์ `Dockerfile` ในระบบ แต่มีไฟล์ `index.html` | - Worker ตรวจพบว่าไม่มีไฟล์เขียนคำสั่งบิลด์<br>- สร้าง fallback Dockerfile ให้เป็นแบบ Web Server Nginx อัตโนมัติ เพื่อให้โปรเจกต์ทำงานได้ |
| **TC-WRK-04** | การบิลด์ Docker Image และการจัดการคอนเทนเนอร์ตัวเก่า | 1. ดำเนินงานต่อในสเต็ปการทำ Image บิลด์และการสั่งรันตู้คอนเทนเนอร์ใหม่ | - หยุดการทำงานและลบคอนเทนเนอร์โปรเจกต์ตัวเก่าออก (หากมีอยู่)<br>- บิลด์ Image ในชื่อ `portfolio-app-<slug>` และเปิดรันคอนเทนเนอร์ใหม่สำเร็จ |
| **TC-WRK-05** | การจัดการเมื่อการบิลด์ล้มเหลว (Fail-safe) | 1. พยายาม Deploy โปรเจกต์ที่ระบุข้อมูล Git URL ผิดพลาด | - สเต็ปบิลด์หรือการ Clone ล้มเหลว<br>- อัปเดตสถานะของไอดีการ Deploy นั้นเป็น `Failed` พร้อมบันทึกข้อผิดพลาด (Errors Logs) ลงฐานข้อมูล |

## 4. การนำส่งทราฟฟิกและการเชื่อมเน็ตเวิร์ก (Nginx & Network Setup)

| รหัสกรณีทดสอบ | หัวข้อการทดสอบ | ขั้นตอนการดำเนินงาน (Steps) | ผลลัพธ์ที่คาดหวัง (Expected Results) |
| :--- | :--- | :--- | :--- |
| **TC-NET-01** | การแชร์กลุ่มเครือข่าย Docker Network | 1. ตรวจสอบว่า Container ทั้งหมดรันอยู่ภายใต้เครือข่ายเดียวกัน | - คอนเทนเนอร์ `portfolio-nginx`, `portfolio-worker` และคอนเทนเนอร์ของโปรเจกต์ย่อยรันอยู่บน `portfolio_network` |
| **TC-NET-02** | การเขียนไดนามิกคอนฟิกและการอัปเดตเร้าต์ของ Nginx | 1. รอให้แอปพลิเคชันย่อยสร้างคอนเทนเนอร์สำเร็จ<br>2. ตรวจสอบว่าคอนฟิกมีไฟล์เพิ่มที่ `/etc/nginx/conf.d/project-<slug>.conf` | - คอนฟิกมีโครงสร้างบล็อก `location /<slug>/ { proxy_pass http://container-<slug>:80/; }`<br>- Worker เรียกคำสั่ง `docker exec portfolio-nginx nginx -s reload` ได้โดยไม่เกิดปัญหาด้านสิทธิ์ |
| **TC-NET-03** | การสตรีมเส้นทางเข้าเว็บแยกโปรเจกต์ (URL Routing) | 1. เปิดเบราว์เซอร์ไปที่ `http://localhost:3000/`<br>2. เปิดไปที่ `http://localhost:3000/<project-slug>/` | - หน้าหลักส่งทราฟฟิกไปยังบริการหน้าบ้าน Next.js<br>- หน้าเดโมส่งทราฟฟิกไปยังคอนเทนเนอร์โปรเจกต์ที่บิลด์สำเร็จอย่างถูกต้อง |
